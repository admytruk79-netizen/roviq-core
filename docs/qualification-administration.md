# Operator qualification reviews

Ops → Qualifications manages actor-specific evidence consumed by the opt-in MACRE case qualification gate. Business-wide service authorizations remain separate in Ops → Eligibility.

An authenticated, active administrator identity is required to write reviews. Shared development admin headers cannot record reviews. The server records the reviewer identity, time, source reference, reason, version, and full before/after audit event in the same transaction. An audit failure rolls back the evidence change. Operators cannot self-verify or read the private registry.

Create a separate record for each evidence document using the exact requirement key, kind and scope registered on a case. Review it as unverified, verified, expired or revoked. Verified evidence requires a nonempty source and either a future expiry or an explicit no-expiry decision. Verification is a human decision after checking the evidence; this does not connect to licensing authorities or issuer APIs. No evidence documents are uploaded by this form.

Existing records keep their subject (actor, requirement key, kind and scope). Reviews can update status, source, expiry and reason. A UUID identifies a record and a version prevents concurrent/stale edits from overwriting a newer decision. Reload after an uncertain request outcome before retrying. Records and review history are retained; there is no delete endpoint. The UI shows the latest 100 audit reviews per actor.

Revocation affects the chosen record. Any other valid matching evidence can still satisfy the requirement. Review all records for that requirement when withdrawing an operator's qualification. Expiry is evaluated at the requested service time by the existing serviceability gate, and at the current time by the Ops preview. A status marked verified can therefore be effectively expired without a scheduled status rewrite.

Reviews lock the actor row, matching the existing authoritative provider selection lock. The preview is read-only and does not authorize assignments. Capacity, geography, business service authorization and the other serviceability rules still apply. Case qualification checks now cover these provider assignment paths: routing and provider selection (serviceability gate), direct Ops offers (`409 qualification_blocked` with the missing items), offer acceptance (re-checked at accept time, `403 qualification_required`), and the open job board (gated jobs are hidden from unqualified technicians and their claim is refused inside the claim transaction). See `src/services/qualification-gate.ts`.

Identified administrators register requirements through `PUT /api/admin/qualifications/cases/:caseId/requirements/:requirementKey` and inspect them through `GET /api/admin/qualifications/cases/:caseId/requirements`. The audited write accepts only triage, diagnostic-pending/in-progress and provider-selection cases with no selected provider. Closed or already-selected cases reject changes. Ops sets requirements from the case page (Job requirements), through the audited requirement endpoint above, which closes once a provider is selected; the same panel lists who qualifies (`GET /api/admin/qualifications/cases/:caseId/candidates`, read-only). This does not establish case-qualification coverage for transport dispatch, parts, mobility or standalone Shop OS execution. Requirements are not inferred from a VIN and there is no issuer catalogue; the panel offers common keys as presets. Cases with no requirements preserve their existing workflow. Migration 201 preserves historical evidence without inventing reviewer provenance. A nonvalidated database constraint protects subsequent writes from blank verification sources; the loader also rejects historical blank or whitespace sources.

Validation covers identified administrator access, private registry boundaries, forged metadata rejection, matching evidence and revocation, expiry, no-expiry review, concurrent review conflicts, cross-actor record-ID collisions, immutable subjects, and atomic rollback on audit failure. Migration testing uses an isolated Neon branch before production rollout.

## Concurrent review and assignment

Transactional offer creation, shop acceptance and open-job claims now lock the actor exclusively before reading qualification evidence. Credential reviews take an exclusive actor lock, so a review that commits first is visible to the assignment check; a review that starts later waits for the assignment transaction. Generic offer acceptance now locks the case, checks qualifications, updates the offer and records its owner in one transaction. Expiry is evaluated after waiting for the lock, rather than at request arrival. Read-only board/candidate previews remain advisory and do not hold transaction locks. These locks serialize application review endpoints; they do not replace database permissions for privileged direct SQL.

Real-Postgres concurrency tests hold an in-flight revocation, start offer acceptance and an open-job claim, observe each waiting for the reviewer lock, then commit revocation. Both requests must reject without accepting the offer, claiming the job or changing the case owner.
