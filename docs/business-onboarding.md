# Business onboarding

In the Actor app, an Ops administrator opens **Businesses** to create one new business location and its initial operator login. Supported workspaces: Shop, Diagnostics, Tow, Parts and Mobility. Existing businesses should use their existing organization and actor records; this flow intentionally creates a new organization.

The form creates an organization, location, actor, password identity and audit entry in one transaction. The actor UUID doubles as a client retry key, protected by an advisory transaction lock. Identical retries return the same business; changed details or credentials conflict. An email collision rolls back the organization, location and actor too. Passwords are hashed through the existing scrypt implementation and never included in business listings, responses or audit metadata. The form keeps the password only in component memory and clears it after success.

`POST /api/admin/business-onboarding` requires an administrator and accepts `requestId`, `role` (`partner`, `diagnostic`, `tow`, `parts`, `fleet`), `businessName`, `operatorName`, `email`, `password` (12–128 characters), and `location` (`name`, `address`, `city`, `region`, two-letter `countryCode`). Returns IDs and `readiness: configuration_required`, never credentials. New requests return 201; identical retries return 200. Conflicts return 409. `GET` on the same path lists the latest 100 businesses provisioned through this flow. Neither endpoint is available to business operators.

The login has only its chosen primary role. Existing per-request identity/actor validation and tenant scoping remain authoritative; suspended actors cannot use an already-issued token. This does not grant additional roles, create capacity, add verified capabilities or enable shop routing. It does not send an invitation or email, verify email ownership/certifications, configure payments, or claim dispatch readiness. Ops must confirm the operator and email separately and arrange credentials through an agreed secure channel. A password reset/invitation flow and multi-operator onboarding remain future work.

For a pilot, configure the business's actual capabilities, service geography, certifications and capacity, connect its systems if needed, and run the existing pilot-readiness checks before assigning customer work. New location addresses are saved without guessed coordinates.

Validation: PostgreSQL-backed acceptance provisions and logs in all five roles, checks least-privilege role grants, cross-shop isolation and token revocation after suspension, exercises simultaneous retries and email-conflict rollback, and rejects invalid role/country/password input. Production browser acceptance checks that Ops can open the new screen and read its registry. It does not create pretend production businesses or contact anyone.
